# Urban Air Quality Assistant — Design

Date: 2026-11-18 · Status: draft for approval
Working name: **Clearday** (placeholder, builder's call — rename freely)

## 1. Intent

Entry for PromptWars Virtual, Challenge 6 "Urban Air Quality Assistant". The brief:

> A GenAI-powered assistant that helps families and communities navigate severe winter smog and urban air pollution. It should suggest low-emission daily routines, indoor air quality hacks, and sustainable alternatives tailored to their location and lifestyle, while clearly explaining the direct impact of their choices.

An AI evaluator scores the public GitHub repo on six criteria: **Code Quality, Security, Efficiency, Testing, Accessibility, Problem Statement Alignment**. A demo video accompanies it. The Challenge 6 submission form asks only for a public GitHub repo (<10 MB) and a video link. There is **no live-URL requirement**, and "use of Google services" is **not** one of this round's criteria (it was in an earlier PromptWars round). Gemini is still the GenAI used.

The user wants the judge to remember two things: **design** (it looks and feels polished) and **accuracy** (everything it says is right and traceable).

## 2. Goals

1. **Global.** Works for any city in the world. Uses the **US EPA AQI** (2024 revision of the PM2.5 breakpoints) and EPA/WHO health guidance.
2. **Live air for the user's location.** Current conditions plus a 5-day hourly forecast, with the source, the timestamp and the fact that the data is modelled shown on screen.
3. **Tailored to lifestyle.** A short household profile drives every recommendation.
4. **Covers the brief's three asks**, each as a visible section:
   - *Low-emission daily routine:* a timeline for today/tomorrow, e.g. when to exercise, open windows, run errands, or take the school walk.
   - *Indoor air quality hacks:* purifier, ventilation timing, cooking, heating.
   - *Sustainable alternatives:* commute mode, heating, waste burning, and so on.
5. **Explains the direct impact** of each choice. Where a cited calculation exists, the impact is shown as a number **computed in code from cited sources**, never generated by the LLM: CO₂ saved, change in PM2.5 exposure, and indoor PM2.5 reduction. Where no solid cited figure exists (e.g. avoiding waste burning, not smoking indoors), the action explains its impact **in words only**, with a source link. No number is better than a shaky one.
6. **An assistant you can talk to.** A follow-up Q&A panel ("Ask about today's air") grounded in the user's current data and the action catalogue.
7. **Polished, accessible UI.** Mobile-first, light/dark themes, WCAG 2.2 AA.

## 3. Non-goals

- User accounts, logins, a database or server-side storage of profiles.
- Push notifications, native apps, offline mode.
- Street-level or sensor-network readings.
- Medical diagnosis or treatment advice beyond EPA/WHO public guidance.
- Production deployment. The submission is the repo plus a video, and running locally for the video is enough. A Dockerfile is welcome but optional.
- Multiple AQI scales (no Indian or European scale switch).

## 4. Anti-goals (failure even if it works)

- **Any number on screen that can't be traced** to a measured or forecast value, or to a cited formula or constant in the code.
- The LLM inventing health claims, emission figures or safe thresholds.
- The Gemini API key reaching the browser, or user free text being able to steer the model into breaking the rules (prompt injection).
- Information conveyed by colour alone (AQI bands must also carry a text label).
- A heavy, slow page. A framework, a chart library or a UI kit pulled in for convenience.
- Advice that doesn't change when the profile or the air changes (it must feel tailored).

## 5. Constraints

- **Stack (decided by the user):** Node.js + Express in **TypeScript** on the server; a frontend with **no framework**, written in HTML/CSS/TypeScript and bundled by **Vite**. Express serves the built frontend.
- **GenAI:** Google Gemini via the `@google/genai` SDK, using the free API key from Google AI Studio. The key comes only from the env var `GEMINI_API_KEY`. The model name comes from the env var `GEMINI_MODEL` and defaults to a current Gemini Flash model (builder: check the current recommended Flash model id at build time). No GCP credits are available, so no paid Google APIs.
- **Air data:** Open-Meteo Air Quality API (`air-quality-api.open-meteo.com/v1/air-quality`). It is free, needs no key, and gives hourly PM2.5, PM10, O₃, NO₂, SO₂ and CO in µg/m³. It is a Copernicus CAMS model, at about 11 km in Europe and about 40 km globally. **Geocoding:** Open-Meteo Geocoding API. Both are free for non-commercial use, under 10k calls/day.
- **Repo:** public on GitHub and **under 10 MB**. No large images or binaries, and no committed build output or `node_modules`.
- **Deadline:** submissions close 2026-11-29 23:59 IST, with at most 3 submissions. Target a first submission by about 2026-11-25 so two retries remain.
- Pushing to GitHub or deploying anywhere happens only with the user's go-ahead.

## 6. Approaches considered

| | Approach | Trade-off | Verdict |
|---|---|---|---|
| 1 | **Express (TS) + no-framework Vite frontend** | Small and fast; full control of the markup for accessibility and design; close to the user's earlier LegalLens stack. UI components are hand-written. | **Chosen by the user** |
| 2 | Next.js (React) for UI and server | Polished component ecosystem, but a heavier bundle, more dependencies and more framework boilerplate, which costs on Efficiency and makes the code harder for a judge to read. | Not chosen |
| — | Calling Gemini straight from the browser | Exposes the API key and fails Security. | Ruled out |
| — | Python / Streamlit | Too little control over design and accessibility. | Ruled out |

Air data: **Open-Meteo** was chosen over Google's Air Quality API (sharper, about 500 m, but needs a billing account with a card) and over WAQI/OpenAQ (station data with patchy global coverage and a token required; no forecast for planning routines).

## 7. How it works

### 7.1 The accuracy rule — "numbers come from code, words come from Gemini"

Three layers, in this order:

1. **Data layer:** fetch hourly pollutant concentrations from Open-Meteo and normalise units.
2. **Deterministic engine (pure TypeScript, fully unit-tested):**
   - **AQI:** computes the US EPA AQI per pollutant from concentrations, using the EPA breakpoint tables (PM2.5 per the 2024 revision; O₃ and NO₂ converted from µg/m³ to ppb at 25 °C). Reports the overall AQI, the category and the dominant pollutant. It does **not** take Open-Meteo's own `us_aqi` field on trust; the app computes and tests its own. Averaging: follow EPA conventions where feasible (PM 24 h, O₃ 8 h). The current-hour "now" figure is labelled as an hourly estimate. Exact averaging is the builder's call, but it must be stated in the UI's "How we calculate" note.
   - **Windows:** finds the cleanest and the worst windows in the next 48 h (e.g. best 2-hour slot for outdoor exercise or for airing the home).
   - **Impact calculators**, each a pure function with its sources cited in a code comment and in the UI:
     - *Commute CO₂:* km × emission factor per mode → kg CO₂e per day, week and year.
       - Fuel-burning modes (petrol/diesel car, motorbike, bus) use UK DESNZ/DEFRA GHG conversion factors, which are tailpipe-based and transfer reasonably across countries.
       - Electric modes (EV, metro/train) use kWh per passenger-km × **the user's country grid carbon intensity**, from a small bundled static table (Ember yearly electricity data, CC-BY 4.0; year and source shown). It falls back to the world average when the country is missing.
       - Bus and train occupancy vary by country, so the UI states the occupancy assumption.
       - The total is limited to these 3 calculators plus the exposure dose (which also covers timing of exercise, the school walk and opening windows). Adding more is optional.
     - *Exposure dose:* concentration × inhalation rate for the activity (US EPA Exposure Factors Handbook, ch. 6) × duration. Used to compare, for example, "running at 7 am vs 6 pm" as a percentage change in inhaled PM2.5.
     - *Indoor purifier:* steady-state indoor reduction ≈ (CADR/V) / (ACH + k_dep + CADR/V), with defaults for air changes per hour and deposition rate taken from cited literature. Room size and purifier CADR are inputs (sensible defaults if unknown, clearly labelled as assumptions).
     - Others the builder adds must follow the same pattern: pure function, cited constant, a test.
   - **Health guidance:** maps AQI category × sensitive groups (from the profile) to EPA's published activity guidance. A static table, not the LLM.
   - **Action catalogue:** a typed static list (around 25–40 actions) across the three brief sections. Each action has an id, section, title, when it applies (AQI range, profile conditions), which impact calculator it uses, a default explanation, and source links.
3. **GenAI layer (Gemini):**
   - Input: the location name, the AQI summary and windows, a **minimised profile**, the **pre-filtered candidate actions with their computed impact figures**, and the health-guidance rows.
     - The minimised profile contains only coarse derived flags (e.g. "sensitive groups: children, respiratory condition"; commute "car, 12 km"; "has purifier") and no free text.
     - The reason: the Gemini free tier may use prompts to improve Google's products. Onboarding shows a one-line notice saying this, and the user's typed Q&A questions are covered by the same notice.
   - Output: **structured JSON** (enforced by a response schema) that picks and orders actions by id, places routine items on the timeline, and writes a short personalised "why this matters for you" for each item plus a one-paragraph day summary.
   - **Number guard:** every digit sequence in Gemini's text must appear among the figures it was given. Otherwise that text is discarded and replaced with the catalogue's default explanation. Unknown action ids are dropped.
   - **Fallback:** if Gemini errors, times out (around 10 s) or fails validation, a rule-based planner builds the same plan from the catalogue. The UI notes "AI summary unavailable" and nothing else breaks.
   - **Q&A panel:** the same grounding context plus the user's question. Answers are scoped to air quality and the user's plan, follow the same number guard, carry a short disclaimer, and come with a polite refusal path for off-topic or medical-diagnosis questions. User text is passed as data inside clearly delimited fields, never concatenated into the instructions.

### 7.2 Household profile (lifestyle inputs)

Kept in the browser's `localStorage` only. It is sent to the server with each request and never logged or stored server-side. Fields (all optional, sensible defaults):

- People: adults, children (<12), older adults (65+), pregnancy, anyone with asthma/COPD or heart conditions.
- Commute or school run: mode (car petrol/diesel/EV, motorbike, bus, metro/train, bike, walk), one-way distance, departure time.
- Outdoor habits: exercise type and usual time.
- Home: air purifier (CADR if known), room size, cooking fuel (gas, electric, solid fuel), heating (gas, electric, wood/coal, none), whether windows can be opened, smoking indoors.

### 7.3 Screens and UI

Single page, mobile-first, readable from 320 px wide up to desktop.

```
┌───────────────────────────────┐
│ Clearday      [📍 Delhi, IN ▾]│
├───────────────────────────────┤
│  AQI 212  ● Very Unhealthy    │  ← big number + colour + text label
│  Main pollutant: PM2.5        │
│  "Keep everyone indoors this  │
│   morning; air improves ~3pm" │  ← Gemini summary (words only)
│  Source: Open-Meteo/CAMS ·    │
│  modelled · updated 14:00     │
├───────────────────────────────┤
│ Next 48 h  ▁▂▅▇▇▅▃▂▁          │  ← hand-drawn SVG, best/worst windows
│ [view as table]               │     marked; table alternative
├───────────────────────────────┤
│ Today's low-emission routine  │  ← timeline cards
│ 07:30  Skip the run → indoor  │
│        −68% PM2.5 inhaled ⓘ  │  ← impact chip; ⓘ shows formula+source
├───────────────────────────────┤
│ Indoor air hacks   (cards)    │
│ Sustainable swaps  (cards)    │
├───────────────────────────────┤
│ Ask about today's air  [___]  │
└───────────────────────────────┘
```

- First visit: a short 3-step profile setup (location, then household, then commute/home), skippable. The profile is editable later from a settings sheet.
- Location: city search with suggestions, or the browser's "Use my location". Coordinates are rounded to 2 decimals before being sent.
- Each impact chip opens a "How we calculated this" popover showing the formula inputs, the assumptions and the source link.
- A "How we calculate" page/section explains data sources, model resolution, the AQI method and the limits.
- Visual design: calm and clean, using the EPA AQI category colours as the only strong colours (tuned so text keeps AA contrast in both themes), and system fonts or one web font at most. The look is the builder's call within these rules. The user cares strongly about design quality, so polish (spacing, motion that respects `prefers-reduced-motion`, loading skeletons, empty and error states) is in scope, not optional.

### 7.4 Server API (sketch; builder may refine)

- `GET /api/geocode?q=` → candidate places.
- `GET /api/air?lat=&lon=` → normalised hourly series, computed AQI now and forecast, windows. Cached in memory per (lat, lon rounded to 0.1°) for about 15 min; repeat requests reuse one fetch already in flight.
- `POST /api/plan` → body `{lat, lon, profile}` → plan (sections, timeline, impacts, summary, `aiUsed: boolean`).
- `POST /api/ask` → body `{lat, lon, profile, question}` → answer.
- `GET /healthz`.

### 7.5 Security

- Every input is validated with a schema (e.g. zod): numeric ranges, enums, string length caps (question ≤ 500 chars), and a JSON body limit of about 10 kb.
- `helmet` with a strict Content-Security-Policy (no inline scripts, self-hosted assets only), and same-origin only (no CORS).
- Rate limits per IP on `/api/plan` and `/api/ask`, which are tighter than `/api/air`.
- Rendering uses `textContent`/DOM APIs only, with no `innerHTML` from model or user text.
- Secrets live in `.env` (git-ignored), with a committed `.env.example`. Errors return generic messages, and stack traces are never sent to the client.
- Logs never contain profile data or questions.
- Timeouts on outbound fetches, and upstream payloads are validated before use.

### 7.6 Efficiency

- No frontend framework and no chart library. Target a JS bundle under 50 kb gzipped.
- Server-side caching and request coalescing as above. Gemini is called once per plan, and the plan is cached client-side until the location, the profile or the hour changes.
- gzip/brotli compression, and long cache headers for hashed static assets.

### 7.7 Accessibility (WCAG 2.2 AA)

- Semantic landmarks, headings and lists, a skip link, a visible focus ring, full keyboard use, and target sizes of at least 24 px.
- AQI shown as number + category text + colour. The chart has a text summary and a toggleable data table.
- `aria-live="polite"` for plan and answer updates. Forms are labelled, and errors are announced.
- Respects `prefers-color-scheme` and `prefers-reduced-motion`, and stays usable at 200% zoom.
- Automated axe checks in the test suite plus a manual keyboard pass.

### 7.8 Testing

- **Unit (Vitest):** AQI breakpoints, including category boundaries and the EPA worked examples; unit conversions; window finder; each impact calculator against hand-checked values; health-guidance mapping; catalogue filtering; the number guard; the fallback planner; input schemas.
- **API (Supertest):** each route's happy path, validation errors, rate limit, Gemini failure → fallback, and upstream failure → clear error. `fetch` and Gemini are mocked; tests never hit the network.
- **Accessibility:** axe-core run against the rendered page (jsdom or a headless browser; builder's call).
- **Coverage target:** at least 80% lines on the server and the deterministic engine. CI on GitHub Actions runs lint (ESLint + Prettier), typecheck (`tsc --noEmit`, strict) and tests.

### 7.9 Repo hygiene (for the Code Quality score)

- Clear folders: `server/` (routes, services, domain), `web/` and `shared/` types. Small modules, no dead code.
- README: what it does and how it maps to the brief, the architecture and GenAI flow (a diagram), the accuracy approach and its sources, setup steps, scripts, testing, accessibility notes, and limits.
- `LICENSE` (MIT), `.env.example`, `.gitignore`, `.nvmrc`/`engines`.

## 8. Left to the builder

- Exact visual style, colour tuning, typography, iconography, microcopy.
- Exact catalogue contents (within the rules in 7.1) and default assumption values (each one cited).
- The current Gemini Flash model id, and the prompt wording.
- AQI averaging details (documented in the UI).
- Choice of supporting libraries (zod, helmet, express-rate-limit, etc.), kept minimal.
- Whether to add a Dockerfile.

## 9. Build order and what slips first

Build in this order, so the app is submittable at every stage:

1. Data layer, AQI engine, windows and impact calculators, with their tests.
2. API routes, security middleware, Gemini plan with number guard and fallback, with their tests.
3. Main page: current AQI card, 48 h chart and table, plan sections, impact chips with "how we calculated" popovers, location search, profile form. Full design polish and accessibility.
4. Q&A panel.
5. README with architecture diagram, CI, axe tests, coverage push.

If time runs short, cut in this order:

1. The 3-step onboarding becomes one plain profile form.
2. The standalone "How we calculate" page is dropped (the popovers stay).
3. The Q&A panel slips to the second submission.

The accuracy rules, accessibility, security and the core test suite never slip.

## 10. Calls made after the builder review (for the user to check)

- No deployment: the submission form asks for no live URL, and Google services aren't a criterion this round.
- Words-only impact for actions without a solid cited figure, instead of forcing a number onto every card.
- Country grid carbon intensity for electric modes (Ember data), UK factors for fuel-burning modes.
- Gemini receives coarse profile flags only, plus an on-screen notice about the free tier.
- The build order and cut order above.
